# 条文ページ作成ワークフロー（必須チェックリスト）

`docs/articles/{kijun,kaishaku,jigyoho}/*.md` を新規作成・全面改修する際は、以下の手順を必ず踏む。

> **戦略ページ（`docs/strategy/*.md`）・テーマ集約ページ（`docs/themes/*.md` の計算系）は本ルール対象外**。それらの作成には [strategy-page-3-layer.md](strategy-page-3-layer.md)（3層分離ルール）を参照すること。

## Step 0: 最新テンプレート解決（必須・最初に実行）

新規・改修いずれの場合も、まず以下を実行してゴールドスタンダードを特定:

```bash
python wiki_quality_check.py --rank --v3 | head -5
```

最上位ファイル（verdict が S か A、最終的に最高点）を **テンプレート** として Read。
複数ページが同点の場合、タイブレーカー（①正確性軸点数→②版数日→③更新日）で1件に絞られる。

**最新確定状況（2026-05-10 v2.7）**:
- `kijun/58.md` v2.7 が **verdict S / 98点** を獲得しゴールドスタンダード地位を継続
- S-rank 7件運用: 58.md（98／数値規定）／ jiko-3.md（97／手続規定）／ jiko-1.md（97／定義条文）／ kijun/1.md（96）／ kijun/10.md（95）／ kijun/15.md（93）／ kaishaku/117.md（90）
- 18項目スコアリング（正確性32 / 試験直結度35 / 学習継続性33）+ 重大欠陥cap 6種で運用中
- 100点満点は意図的に困難（誤判定防止）。テンプレ参照は **記事タイプ別の3記事** を使い分ける：**kijun/58.md（数値規定系）** ／ **jiko-3.md（手続規定系・折り畳み原文の参考実装）** ／ **jiko-1.md（定義条文系）**

**Sprint 履歴**:
- 2026-05-05 v2.3: kijun/58.md が単独で verdict A / 80点を獲得しゴールドスタンダード確定
- 2026-05-06 v2.4: 学習者目線の条件付セクション運用導入（★0/★6/★17）
- 2026-05-09 v2.6: 3列翻訳テーブル等 必須ブロック8パターン確立 → 58.md・jiko-1.md 双方反映
- 2026-05-10 v2.7: **#9 条文原文 全文折り畳み・#10 黄色マーカー凡例＋根拠表** を追加（10ブロック化）。jiko-3 ChatGPT検証で発見した7アンチパターン（PCB誤記・第N項取り違え・原因フィルタ・検索漏れ・単純化要約・義務者曖昧化・条文用語口語化）を「再発防止」として明文化

**18項目すべてが満点不可な記事タイプ**:
- **I09（過去問リンク）**: 該当条文の過去問が無い場合は満たせない
- **I13（3列翻訳）**: 用語定義条文・短い手続規定など、原文ブロック分解が不要な記事タイプでは満点不可
- これらが満たせなくても無理に追加しない。記事タイプに合った項目で点数を稼ぐ

**改善ナビ機能の使い方**:
- `python wiki_quality_check.py <article_path> --v3` の出力末尾に「💡 改善ナビ: 不足項目TOP3」が表示される
- 次に着手すべき改善対象はこの3項目から選ぶ（点差が最大の項目を優先）
- スコア最大化目的で全18項目を闇雲に埋めるより、改善ナビTOP3を順に潰す方が効率的

**禁止**: CLAUDE.md やメモリの「kijun/X.md がゴールド」記述だけ信じてファイルを開く（古い情報の可能性）。worktree 内の古い CLAUDE.md コピーは特に注意。`--rank --v3` 出力が真のゴールド指定。

## テンプレートv2.7 必須ブロック仕様（2026-05-10 確立／旧 v2.6 を拡張）

### v2.7 必須ブロック検証コマンド

執筆完了後、以下を実行して S-rank 達成を確認：

```bash
python wiki_quality_check.py docs/articles/{kijun,kaishaku,jigyoho,other}/{file}.md --v3
```

判定基準:
- **S-rank（90点以上）** → push 可
- **A-rank（80〜89点）** → 改善ナビ TOP3 を潰してから push
- **B-rank以下（79点以下）** → 8 必須ブロックのどれが欠落か再点検

### Step 6 ユーザー先見せの追加チェック項目

`Step6: ユーザー先見せ` の構造ドラフト提示時、上記 8 ブロックが章立てに **どこに配置されるか** を併記する。例：

```
- 章立て: [14セクション+監修ログ・テンプレ準拠]
- v2.7 必須ブロック配置:
  - 1. 💡5秒で思い出す: メタ概要直後
  - 2. 数値検証 PASS: §6 直前（H3 + 標準テーブル・admonition不可）
  - 3. 改変明記: §6 末尾の出題実績まとめ note
  - 4. 3列翻訳テーブル: §13 用語集サブ
  - 5. 🟢軽度: §5 ひっかけ末尾
  - 6. mermaid/SVG: §4 因果理解
  - 7. 実務キーワード: §3/§5/§9 散りばめ
  - 8. 重要度bold: メタ「**重要度**: A」
  - 9. 📜条文原文 全文折り畳み: §2 冒頭（??? note "📜 条文原文 — eGov 完全版"）
  - 10. マーカー凡例＋根拠表: 折り畳み内（過去問実出題実績ある語のみ <mark>）
```

これによりユーザー側で「3列翻訳テーブルは絶縁系条文だと冗長になる」等の早期フィードバックを得られ、push後の手戻りを防ぐ。

### 設計思想（なぜこの10ブロックか）

- **試験得点直結度（I02/I06/I07/I10/I12/I13）** を最優先 → 学習者の合格貢献
- **学習継続性（I14/I15/I17）** → 復習サイクルでの再訪率向上
- **正確性（I02 数値検証 + I05 出典／#9 条文原文 全文折り畳み + #10 マーカー凡例）** → 誤情報配信の予防＋条文文言の一次照合源
- 既存の I04/I08/I09/I11/I16/I18 は v2.4 までのテンプレで既に充足するため v2.7 では追加要件なし

### 禁止事項（v2.7）

- ❌ 「3列翻訳テーブルは記事タイプ的に不要」と判断して省略する（**全 4 タイプで必須**）
- ❌ 重要度ランクを `**重要度**: **A**` のように ABC を二重bold で包む（検出失敗）
- ❌ 数値検証 PASS の根拠列を省略（出典条項なき PASS は虚偽記載扱い）
- ❌ **admonition で表を包む**（`!!! success` 内に `| ... |` テーブル）— admonition 枠 + テーブル枠で「二重枠」となり視認性低下。テーブルはフラット配置・タイトルは H3 見出しで（2026-05-10 教訓）
- ❌ **eGov 一次照合なしに条文原文を要約・改変する** — 折り畳み原文ブロック（必須#9）は eGov 法令検索 から取得した正本のみ掲載。要約・解説は折り畳みの外（既存 §2 本文）に分離（2026-05-10 jiko-3 PCB誤記事件・第N項取り違え事件 教訓）
- ❌ **`<mark>` を予想・想定の語に付ける** — 黄色マーカーは過去14年で **実際に穴埋め出題された語のみ**。予想・論述頻出語は `**bold**` で区別（feedback_denken_wiki_marker.md 規約）

## 背景（なぜ必要か）

- 電技解釈は数年置きに改正され、**条番号が変わる** ことがある（特に分散型電源系 §220台）
- ローカル `_data/kakomon.yml` の `topic` 文字列を盲信すると、改正前の論点で書いてしまうリスクがある
- 過去事例（2026-05-02）：第224条を「低圧連系の保護装置」（旧版）で書いたが、現行は「高圧/特別高圧連系の再閉路防止」だった

## 必須チェックリスト（ページ作成前）

```
□ Step1: kakomon.yml で該当条文の出題実績を確認
   python -c "import yaml; data=yaml.safe_load(open('_data/kakomon.yml',encoding='utf-8'));
              [print(p) for p in data['problems'] if '§{条番号}' in p['article']]"

□ Step2: denken-ou.com で最新出題例の論点を確認
   - URL パターン: https://denken-ou.com/houkir{年}-{期}-{問}/
     例: R6下問7 → houkir6-2-7、R7上問4 → houkir7-1-4
   - 最低1件、出題実績がある場合は最新年度を確認

□ Step3: kakomon.yml の topic 文字列と denken-ou.com の論点を照合
   - 一致 → そのまま執筆
   - 不一致 → 法令改正で内容が変わった可能性。e-Gov公式で現行条文を確認
   - kakomon.yml 側を修正してから執筆

□ Step4: e-Gov 法令API（または経産省PDF）で条文タイトル・本文を照合
   https://laws.e-gov.go.jp/ で「電気設備の技術基準の解釈」を検索
   タイトルが正本と一致しているか確認

   ★ v2.7 必須ブロック#9 用に **eGov XML 一次取得**:
     curl -s "https://laws.e-gov.go.jp/api/1/lawdata/{LawId}" --max-time 60 -o /tmp/law.xml
     - 主要 LawId: 報告規則=340M50000400054 ／ 電技省令=409M50000400052 ／ 電気事業法=339AC0000000170 ／ 施行規則=407M50000400077
     - XML 内の `<Article Num="N">` `<Paragraph Num="M">` `<Item Num="K">` 構造で項・号番号を確認
     - **テーブル内テキストも `<TableColumn>` まで探索**（A4 教訓：検索ゼロ件＝存在しない、と早合点しない）

□ Step5: 確信度自己評価
   - 条文タイトル: 90%以上か？ → No なら e-Gov 再確認
   - 出題内容: 90%以上か？ → No なら denken-ou.com 再確認
   - <70% の項目は [要確認] フラグ付きで記載

□ Step6: ユーザー先見せ（本文執筆前・省略不可）
   - 構造ドラフトをユーザーに提示してから本文執筆へ
   - 提示フォーマット：
     - 条文タイトル: [Step4で取得した正式タイトル]
     - 出題実績: [Step1で確認したN件・年度内訳]
     - 章立て: [14セクション+監修ログ・テンプレ準拠]
     - 主要数値: [Step4で取得した数値リスト]
     - 関連条文: [対比・参照する他条文と取得済み数値]
     - **v2.6 必須ブロック配置**: 8ブロック（5秒・数値検証PASS・改変明記・3列翻訳・🟢軽度・mermaid/SVG・実務・重要度bold）の配置位置 → 詳細は本ファイル「テンプレートv2.6 必須ブロック仕様」参照
     - → 「この構成で本文執筆に進んでいい？」と明示確認
   - Step6で指摘を受けて構造修正できれば、push後の revert 不要
   - 例外条件: ユーザーから「直接執筆していい」と明示許可がある場合のみ省略可
```

## 改正情報・番号ズレの記載ルール（記事側の必須要件）

法令改正で条番号や内容が変わった、または **既存記事の条番号が現行と異なる** ことが判明した条文は、**記事冒頭に必ず注記ブロックを配置する**。学習者が混乱しないようにすることが最優先。

### 2つのケースを区別する

| ケース | 判定方法 | 注記の見出し |
|--------|---------|------|
| **A. 法令改正で番号が変わった** | 経産省告示・JESC・電気書院追補版に改正記録あり | `📌 法令改正による条番号変更` |
| **B. 記事側の番号誤り（改正記録なし）** | 改正記録は無いが現行と既存記事の番号がズレている | `⚠️ 条番号誤記の訂正` |

**判定不能なら `[要確認]` を必ず付ける。** 「改正されたらしい」のような根拠なしで A を選択しない。

### 必須フォーマット（冒頭メタ直下に配置）

```markdown
!!! warning "📌 改正注意（条番号・内容の変動）"
    - **本ページの条番号**: 第NNN条（kakomon.yml・既存リンク互換のため維持）
    - **現行条番号**: 第MMM条（YYYY年MM月改正以降）
    - **改正前の対応**: 旧第NNN条 = 「○○○」
    - **改正根拠**: [経産省告示 第○○号](URL) / [JESC 改正情報](URL)（${改正年月日}公布・${施行年月日}施行）
    - **試験対策の注意**: R06以降の出題は **現行第MMM条** として解説される。穴埋めの空欄語句は変わらないが、関連条文の番号は現行体系で覚えること。
```

### 改正根拠の必須要件（出典なき注記は禁止）

| 項目 | 必須/任意 | ソース候補 |
|------|:---:|------|
| 改正年月日（公布日） | 必須 | 経産省告示・JESC改正履歴・官報 |
| 施行年月日 | 必須 | 同上 |
| 出典URL | **必須**（最低1本） | 経産省 `meti.go.jp/policy/safety_security/...` / JESC `jesc.gr.jp/revision/` / 電気書院 追補版PDF |
| 改正前後の条番号対応 | 必須 | denken-ou.com 解説 vs e-Gov 現行条文 |

**出典が取れない場合は `[要確認]` フラグを付ける。**「改正されたらしい」「番号が変わったようだ」のような根拠なし記述は禁止。

### 適用判定フロー

```
□ kakomon.yml の article 番号と denken-ou.com 解説の条番号が異なる
  → 改正の可能性あり。e-Gov/経産省で現行条番号を確認
□ 現行と旧で番号が異なる確証が取れた
  → 改正注記ブロックを記事冒頭に配置（必須）
□ kakomon.yml の article を現行番号に揃えるかは別判断（一括修正は影響大）
  → 暫定は記事内の注記で吸収、根本対応は別タスクで一括修正
```

### ファイル名・URLの扱い

- 既存ページの URL は **学習コンテンツの被リンク互換** を優先して原則維持
- リネーム（例：`227.md` → `229.md`）は kakomon.yml・関連ページ全体を一括棚卸しできる別タスクで実施
- リネームしない場合は記事冒頭の改正注記で吸収する

### 禁止事項

- ❌ 条番号がズレている事実を確認しながら、注記なしで本文だけ書き換える
- ❌ 「（改正で番号変わった）」のような曖昧な1行で済ませる（学習者が見落とす）

## 認知需要チェックリスト（学習者の理解視点で初版を仕上げる）

`wiki_quality_check.py` で 100/100 でも、学習者から「この用語混同する」「数値の根拠が分からない」「位置関係が見えない」と質問が来ることがある。**構造完成と認知補助は別の指標**。初版の段階で以下を埋めておくと反復回数が減る。

### 必須チェック（4項目）

```
□ A. 混同しやすい用語はないか？
   → 似た名前で別物の用語があれば、§4冒頭に「○○ vs ○○」整理ブロックを配置
   - 比較表（何を指す／言い換え）
   - レイヤー違いの図解（場所の名前 vs 製品の名前 等）
   - 誤答ひっかけ警告（試験で出る誤答パターン）
   例: 117条「引込線（ルート）vs 引下げ用電線（製品）」

□ B. 出てくる数値の物理的根拠は説明したか？
   → 「8.01kN／5mm／3.5m」のような数値は丸暗記対象に見えるが、
     物理現象・JIS規格・身体感覚にひも付けると記憶が定着する
   - 各数値ごとに「なぜこの値か」を §4 に「数値の根拠」サブセクション
   - 教育的近似を書くときは必ず公式根拠ガード（後述）を併記
   例: 「直径5mm 硬銅線 = 8.01kN」は1セットで覚える／3.5m=歩道橋上と同じ思想

□ C. 場所・モノの位置関係を視覚化したか？
   → 施設規定（電線路・支持物・離隔）はテキストだけだと位置関係が伝わらない
   - 電柱・建物・電線ルートを SVG で図解
   - ハイライト矩形でその条文の対象範囲を明示
   - 関連用語が出る別の場所も併記（例: 配電柱内の高圧引下げ線 vs 需要家への高圧引込線）

□ D. 関連用語の "別物だが似た名前" の罠を表で潰したか？
   → 同じ漢字・似た音の別概念がある条文は、表で「これは何、これは別物」を整理
   - 例: 引込線 vs 引下げ線、A種接地 vs A種特別高圧、認可 vs 届出 vs 報告
   - 試験ひっかけと実務混乱の両方で出る

□ E. 用語定義条文での「断定回避」を確認したか？
   → 用語定義条文（第1条等）では「○○ではない」と断定する表現を避ける
   - 例: 「機器外箱は電気機械器具ではない」（危険）
     → 「機器外箱は通常 電路ではない（非充電部）→ A・C・D種接地の対象」（安全）
   - 充電部 vs 非充電部、電路 vs 機器外箱 のサブタイプを明確に区別
   - !!! warning ブロックで「試験での整理」を明示すると安全
```

### 教育的近似ガード（数値根拠を書くときの必須）

物理現象から数値根拠を説明するときは、**公式根拠ではない**ことを必ず明示する。

```markdown
!!! warning "本セクションは "暗記補助のための物理イメージ" — 公式根拠ではない"
    以下の数値導出は **教育的近似** であり、規格機関（JIS委員会・経産省）の
    公式な決定根拠そのものではない。
    - [近似の限界1：典型値での目安計算であって規格の正確値ではない 等]
    - [近似の限界2：条文がこの計算で導出されたという公式記録はない 等]
    **試験対策上は規格値を覚えるのが正解**。本セクションは「なぜその値か」を
    体に染み込ませて忘れにくくするための補助。「公式の導出」と混同しない。
```

詳細は `~/.claude/projects/.../memory/feedback_pedagogical_approximation_guard.md` 参照。

### 記事タイプ別の重み付け

| 記事タイプ | A. 用語整理 | B. 数値根拠 | C. 位置図解 | D. 類似名罠表 |
|---|:---:|:---:|:---:|:---:|
| **数値規定**（58条等：絶縁抵抗値・電圧区分） | △ | ◎ | △ | △ |
| **施設規定**（117条等：電線・高さ・配置） | ◎ | ◎ | ◎ | ◎ |
| **手続規定**（保安規程・届出・許可） | ◎ | △ | △ | ◎ |
| **法令体系**（事業法・施行令） | ◎ | ✕ | △ | △ |

`◎` = 必須、`△` = 該当があれば推奨、`✕` = 通常不要

### 適用タイミング

- ✅ 新規記事の **初版執筆前** に4項目をスクリーニング → 該当があれば §4 内のサブセクションを設計に組み込む
- ✅ ユーザーから「○○の違いが分からない」「○○の根拠が分からない」と質問が来たら、その記事の認知需要チェックを再実施し、初版で見落とした項目を反映
- ❌ 100/100 のスコアだけで「完成」と判断しない（構造完成 ≠ 学習者の理解）

### SLD（単線結線図）作成ルール

電気機械器具を扱う条文（第1条等）でSLDを描く場合、**接続形態を3分類で明示**する:

| 分類 | 例 | 描画方法 |
|---|---|---|
| **① 主回路（直列）** | DS・CB・CT一次・変圧器・開閉器・電動機 | 太線（2.5px）の横方向で連結 |
| **② 並列・分岐** | VT・避雷器（LA）・SPD | 主回路から下方向に細線（1.2px）で分岐 |
| **③ 信号・制御系** | 保護継電器 | 破線（dasharray="4,3"）で別ボックスに |

凡例で太線/細線/破線の意味を必ず併記する。LA・VT等を主回路に直列配置すると誤解を招く。

### §5 頻出ひっかけのカテゴリラベル運用（コンポーネント改造なし）

著者は番号リスト各項目の**先頭**に運用ルールとしてカテゴリラベル `[①〜⑥]` を付与する。**少なくとも該当カテゴリは各1項目以上ラベル付きで含める**。Markdown 記法のみで対応（self-check.js / custom.css は触らない）。

```markdown
1. 🔴 **[③手続き]** 保安規程は経済産業大臣の**認可**を要する → 実際は**届出**（電気事業法 §42 第1項）
2. 🔴 **[②主語]** 第1条は「使用者」を保護する規定 → 正しくは**人体**を保護
3. 🟡 **[①数値]** D種接地は10Ω → 正しくは**100Ω**（A種が10Ω）
4. 🟡 **[⑥例外]** ただし書き・除外条件を読まずに原則だけで判断する
```
