# Claude Code 作業ルール

このプロジェクトは、電験3種学習者向けのWikiを作成・改善するためのものです。
目的は、正確で、試験対策に役立ち、初学者にも読みやすいページを作ることです。

## 1. 基本方針

- 回答は前置きせず、結論から始めること。
- 不明点・不確実な点は推測で補完しないこと。
- 法令、制度、数値条件、条文番号、試験頻出論点は特に慎重に扱うこと。
- 情報の正確性が必要な場合は、経産省、e-Gov、電気技術者試験センターなどの正式情報を優先して確認すること。
- ChatGPTアドバイスを確認して、対応が必要なものは修正して。

## 2. スコープ厳守

- 私が依頼した範囲だけを変更すること。
- 関係ないファイル、関係ないセクション、関係ない文言は変更しないこと。
- 「ついでに改善できそう」と思っても、勝手に変更しないこと。
- 追加改善案がある場合は、実装せずに「提案」として最後に分けて書くこと。

## 3. 大きな変更の前に確認

以下の変更を行う前には、必ず一度止まって説明すること。

- ページ構成を大きく変える
- 既存セクションを削除する
- 見出し構成を大きく並べ替える
- 複数ファイルを横断して変更する
- 既存の説明方針や学習導線を変える
- build、deploy、公開、外部送信などの操作を行う

説明するときは、以下を示すこと。

- 何を変えるのか
- なぜ変えるのか
- 影響するファイル
- 元に戻せるかどうか

私の明示確認なしに実行しないこと。

## 4. 最小変更を優先

- まずは最小限の修正で目的を達成すること。
- 大規模リファクタより、試験対策上の誤解を減らす修正を優先すること。
- UI改善も、学習効果に直結するものを優先すること。
- 装飾や見た目の改善だけで本文の正確性を崩さないこと。

## 5. 電験3種Wikiとしての確認観点

修正時は、必ず以下を確認すること。

- 電験3種の受験者にとって得点につながるか
- 初学者が誤解しやすい表現になっていないか
- 条件、例外、対象範囲、主語が明確か
- 「届出」「許可」「認可」「承認」「報告」「通知」を混同していないか
- 数値条件、未満・以下、以上・超過の境界が正しいか
- 計算問題では、単位、前提条件、途中式、選択肢との対応が正しいか
- 法規ページでは、正式情報に照らして誤りがないか

## 6. ChatGPTレビュー反映ルール

ChatGPTからレビュー・改善提案・指摘がある場合は、以下の手順で対応すること。

1. ChatGPTアドバイスを確認する
2. 指摘を以下に分類する
   - 必ず修正すべき誤り
   - 修正した方がよい改善点
   - 参考意見に留めるもの
   - 対応不要なもの
3. 必ず修正すべき誤りから優先して対応する
4. 対応不要と判断したものは、理由を明記する
5. 勝手に大規模改修せず、依頼範囲内で反映する

## 7. 作業後の報告

作業完了後は、必ず最後に以下を簡潔にまとめること。

- 変更したファイル
- 変更した内容
- 変更しなかった箇所
- 確認が必要な点
- build/test結果
- 次に対応した方がよい提案
- **今回の学び**（下記スキーマ・どちらか必須）

### 「今回の学び」スキーマ（v3・必須フォーマット）

以下2フィールドのいずれか一方を必ず出力。両方なしは禁止、両方併記も禁止、自由文形式は禁止。

```
今回の学び:
  memory_created: <作成した memory の slug 名（例: feedback_xxx）。絶対パス・保存先は不要>
```

または

```
今回の学び:
  memory_skipped: <理由>
```

#### memory_created の場合

- 値は **memory の slug 名** で十分。絶対パス・保存先は記載不要（古舘さん「保存先不問」・2026-06-18）
- 学びの L4/L5/L6 区分・本文・関連 link は memory ファイル本体に書く（§7 では slug だけ）
- 機械的な path 検証 hook は **無い**（v2.1 が前提とした `learning_memory_check.py` は実機に未配線と判明・2026-06-18）。古舘さん事後 review が担保

#### memory_skipped の場合

- 理由は **具体的に1行**。許容例：「既存パターン反復・新規抽象化なし」「`[既存 memory name]` でカバー済」「軽微作業で学び抽出対象外」
- 「学び無し」「特になし」だけは NG（PDCA Check 証明にならない）

### 禁止語彙（先送り表現・即 §7 違反）

以下を §7「今回の学び」で使用した時点で work-rules §7 違反（機械検出 hook は無い・古舘さん事後 review が担保）。

- ❌ 「Rule of Three N/3 で保留」「2回目発生時に memory 化判定」
- ❌ 「候補として後で memory 化」「次回検討」「次回類似時」「将来 Skill 化」
- ❌ 「次回からは X する」「次回は Y を意識する」
- ❌ 「memory 化検討」「memory 化保留」「memory 候補」「あとで memory」

Rule of Three は [feedback_rule_of_three_skill_trigger]（**Skill 化** 三回則）であって memory 化判定ではない。混同事例：2026-05-31 セッション。学びが「即 memory 化レベルでない」と判断するなら memory_skipped に書く。

### 「次の提案」と「今回の学び」の境界

| 項目 | 性質 | 内容 |
|---|---|---|
| 6. 次に対応した方がよい提案 | **未来向け・行動** | TODO候補・punch list・実装せず提案のみ |
| 7. 今回の学び | **過去向け・認知** | 抽象化された原則／プロセス改善／横展可能パターン → 即 memory 化 |

## 8. MEMORY.md 運用

重要な判断をした場合は、MEMORY.mdに記録すること。

記録する内容は以下。

- 決定したこと
- その理由
- 採用しなかった案
- 次回以降に引き継ぐ注意点

ただし、軽微な文言修正や一時的な作業ログは記録しなくてよい。

## 9. ERRORS.md 運用

同じ修正で2回以上失敗した場合、または原因調査に時間がかかった場合は、ERRORS.mdに記録すること。

記録する内容は以下。

- 何がうまくいかなかったか
- 原因
- 最終的にうまくいった方法
- 次回同じ失敗を避けるための注意点

## 10. 禁止事項

- 根拠のない法令説明を追加しない
- 試験対策上、誤解を招く簡略化をしない
- 依頼外のファイルを勝手に変更しない
- デザイン改善のために本文の意味を変えない
- buildエラーを隠さない
- 不確実なことを断定しない
- 私の確認なしにdeploy・publish・外部送信をしない

## 11. タスク完了宣言の前の L4-L6 セルフチェック（必須）

「完了報告」「タスク完了」「以上です」を書こうとした瞬間に、以下4問を必ず自問する。
1つでも空欄なら、完了ではなく **「次層への昇格判定」段階** に戻る。

### 4問セルフチェック

1. **L4「概念」**：成果物に **核心キーワード／本質的論点** が明文化されているか？文言一致確認・形式整形だけで終わっていないか？
2. **L4.5「adversarial」**：自分の実装/規律/hook が **「壊れる入力」を3パターン以上自分で書いて回したか**？success path test（正常入力で動く）だけで完了宣言していないか？
3. **L5「プロセス」**：同種のミス・取り逃しが繰り返されているなら、**memory ファイル化して恒久対策**しているか？
4. **L6「システム」**：同じ規律が適用できる **類型ページが他にあるなら、punch list を自発的に作成**しているか？

### L4.5 adversarial の具体プロトコル

実装直後は「動いた喜び」で完了宣言バイアスが極大化する（正解側思考停止）。これを防ぐため、完了宣言前に以下3パターンを能動的に書いて回す:

| 実装 type | adversarial 3パターン最低例 |
|---|---|
| regex / parser | 空白含む input・引用符付き input・改行折り返し・対象が議論文中で言及・case 違い |
| path 検証 | スペース含む path・絶対/相対混在・引用符付き・末尾 punctuation・日本語/Unicode |
| hook | 自己ブロック発火・code block 内引用・再帰・timeout 超過 |
| API/script | 空 input・巨大 input・想定外 type・並行実行・network 切断 |
| 文書/規律 | 規律違反の正確な書き方（escape ルート）・本人が書きそうな先送り語彙・形だけ pass の dummy |
| Wiki記事 | 数値境界（以下/以上の誤読）・隣接条文の引用ズレ・改正前後の混同・選択肢「正しいもの／誤っているもの」反転 |

回答テンプレ:
```
adversarial:
  パターン1: <具体的な壊す入力> → 期待 vs 実測
  パターン2: 同上
  パターン3: 同上
```

3つすべてに具体回答が書けない時点で完了宣言禁止。詳細プロトコル: [memory: feedback_adversarial_verification_default]

### 完了 ≠ 終わり

完了宣言は「タスク終了」ではなく **「L1-L3 から L4 への昇格判定」**。4問すべてに具体的な回答が書けるまで完了宣言は禁止。
